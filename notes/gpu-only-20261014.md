# Strict GPU pixel path on Windows, 2026-10-14

Local continuation toward 0.0.1.2 (planned as 0.0.1.3). The owner requires the image to remain on the
GPU from capture through processing and return. Tested at dfb2143; prepared for
owner-requested publication into improve-e4m3. No tag or release.

## Pixel residency contract

The same-Arc path is:

`swapchain image -> exported device buffer -> imported device buffer -> GPU decode/
resize/features -> resident network -> GPU composition/history -> exported output
buffer -> swapchain image`.

No raw frame, prepared feature array, neural head or image-history array is
viewed, decoded or downloaded by the CPU on this path. Vulkan copies and compute
perform the work. Weights upload during startup; the CPU records commands,
coordinates ownership/synchronization, handles settings and reads reduced
metadata. Zero CPU execution is not a possible Vulkan/Python application contract.
Host-mappable graph storage on UMA does not mean the CPU reads its activations.

The earlier implementation could silently select a compatible host pixel path.
`NR_GPU_ONLY=1` now forbids that fallback in both the game layer and daemon:

- The layer skips host allocation/capture, cached-image writeback, async exchange,
  photo/capture/dump processing and stale legacy reply reads.
- If shared processing is unavailable, unsupported or fails, it presents the
  game's original image, preserving WSI wait ownership and timeout-safe cleanup.
- The daemon rejects legacy plain/masked headers before reading pixel payloads.
  The separate host processing entry is also guarded against direct invocation.
- With strict mode unset or `0`, the prior compatibility route still works.

The setup window's experimental GPU option writes `NR_GPU_IMAGE=1`,
`NR_GPU_TRANSPORT=1` and `NR_GPU_ONLY=1`. Turning it off explicitly clears all
three. It remains off by default. EN/RU/ES text explains original-frame retention
and the current same-Arc, every-frame, synchronous SDR requirements. Unsupported
async/every-N settings keep the requested pacing and skip the effect.

After a fatal exchange failure shared transport remains disabled for that Vulkan
device lifetime. Daemon restart alone leaves strict mode presenting original
frames; restarting the game/device negotiates shared transport again. This does
not automatically enable an unsafe semaphore/fence retry.

## Reduced metadata

The first per-block reduction stays in an unmapped DEVICE buffer. A second GPU
pass returns one exact uint count for nonfinite head values (4 bytes), or an FP32
high/low compensated sum plus status for delta (12 bytes). No shaderFloat64
capability or runtime device feature change is required.

Ordinary positive normal-image delta has a conservative error bound below
7.1e-10 for at most 2^22 pixels, three channels and mean at most one. Cut decisions
pass `live.cut_limit`: if the uncertainty interval overlaps the threshold, or
partials are subnormal/overflow, only the reduced partials are copied to HOST_READ
scratch and summed with the old FP64 host reduction. No image is downloaded even
on this rare boundary path. NaN/Inf status and uint counts retain their semantics.
The existing first-stage reduction versus NumPy ordering limitation remains.
Letterbox bounds still use line maxima, or eight cached-line checks.

## Complete present measurements

Arc 140V (8GB), Vulkan 1.4.359 / Intel 101.9150. Normal desktop user execution,
Khronos synchronization validation, real hidden Win32 swapchains and full model.
Each run has 55 frames per extent: 25 warm-up and 30 timed samples. Both runs
processed exactly 110 shared GPU frames, with zero CPU pixel requests and zero
validation errors. Protocol 1 used exported binary semaphores.

| Output / network scale | Complete present median / p95 |
| --- | ---: |
| 1920x1080 / 0.4 | 77.29 / 85.69 ms |
| 2560x1440 / 0.4 | 119.70 / 125.12 ms |
| 1920x1080 / 1.0 | 408.43 / 417.39 ms |
| 2560x1440 / 1.0 | 808.82 / 815.67 ms |

Scope: `vkQueuePresentKHR`, including layer capture, daemon processing, return
and downstream WSI. Game rendering/acquisition outside this call is excluded.
The fixture clears changing synthetic colors; it is not a real game FPS result,
a matched CPU/GPU A/B, or directly comparable with the earlier daemon-only random
image benchmark. Layer stage timings are host wall durations, including scheduling
and waits, rather than GPU timestamp durations. At 1440p/0.4 capture/return median
was about 0.48/1.30 ms; exchange/processing dominated.

Results: `work/gpu-only-highres-04-9150/summary.json` and
`work/gpu-only-highres-10-9150/summary.json`. Each records actual extents, driver,
binary/shader hashes, all shared frames, warm timing counts and validation state.

Public numeric samples and paired E4M3 timings are available in
[measurements/windows-arc140v-20261014.json](measurements/windows-arc140v-20261014.json).
The export excludes local paths, process/control logs, weights and image data;
durations are rounded to six decimal places in milliseconds. It retains the
different measurement scopes instead of treating these values as game FPS.

## Validation and public Linux context

Layer x64/x86 and shaders/runtime rebuilt through the MSVC build script.
14 host CTests pass, including strict-policy mocks. Portable daemon codec/request/
letterbox checks pass; its Unix-socket integration is a Linux-only check.
Stats: 12 tests pass including actual GPU scalar/old-partial comparisons,
threshold zero/nextafter protection, subnormal/overflow, NaN/Inf and exact count
2^24+1. Full-model pipeline: four tests pass, including eight byte-identical
frames and FP32 histories while DEVICE image views/downloads are forbidden.
Wizard/bridge: 85 checks with one platform skip; WPF self-test passes.

Additional actual Win32 cases all passed with zero CPU pixel requests and zero
synchronization errors:

| Case | Shared frames / presents | Evidence under work/ |
| --- | ---: | --- |
| High-resolution forced private fences | 16 / 16 | gpu-only-highres-fenced-9150 |
| Vulkan 1.1, off/on, scale changes, resize | 22 / 24 | gpu-only-api11-controls-9150 |
| Unsupported async, exact original pixel | 0 / 16 | gpu-only-unsupported-async-final-9150 |
| Unsupported settings, exact original pixel | 0 / 16 | gpu-only-unsupported-settings-9150 |
| Owned daemon stop/restart, original retained | 2 / 16 | gpu-only-restart-final-9150 |

The last case verifies original pixels at the outage frame3 and a fresh frame5
after daemon restart, and observes zero host fallback frames. These optional
diagnostics read one four-byte pixel per check; ordinary positive runs perform
no pixel readback. The harness rejects missing timings, duplicate/incorrect
frame IDs, wrong actual extents, unlabeled successful daemon frames, CPU layer
timing requests and synchronization-validation errors. Owned children are stopped.

The public Linux branch `experiment-bgra8-pipeline` at `2b8c1d6` contains
[improve-bgra8-pipeline.md](https://github.com/Uzbekunknown/dlss-nr-on-intel/blob/2b8c1d691e810b56fa7c087e5f10d800d7ceb333/notes/improve-bgra8-pipeline.md).
It describes the gated native CPU `NR_HOST_BGRA8` decode/resize/compose experiment,
not GPU-resident capture. Reviewed public issue/PR discussions did not establish
the claimed Linux full-GPU note; a private conversation may contain other work.
That experiment has not been merged here.

## Verification of the combined publication branch

The `improve-e4m3` integration retains the E4 source, attribution/license and
`--shader-dir` tool. `NR_E4M3_MAGIC` remains default 0. All 26 default SPIR-V files
from a fresh MSVC build match the tested Windows continuation byte for byte.
GEMM contract, frame execution and full-model image pipeline regressions pass.
The combined build also passed 16 strict actual Win32 1080p/1440p presents with
zero CPU pixel requests and zero synchronization-validation errors.

Before release claims: real-game same-adapter A/B and matched B580 measurements.
Current work proves strict pixel residency in controlled supported cases; it does
not make unsupported settings process on GPU or promise a threefold FPS gain.
